## Part A — Spec (what "done" means)

The branch is ready to merge when all of these hold:

1. **Gates green on the final head**, run by the coordinator on a clean checkout:
   fresh-DB SQL apply `0001`–`0026` + second apply of `0025`/`0026`; `db/tests/*.sql` all PASS;
   `bun run tsc --noEmit` 0 errors; `bunx eslint .` 0 errors and no new warnings (baseline 8);
   `bun run test` with a real DB 0 failures; `NITRO_PRESET=node-server bun run build` exit 0;
   `src/routeTree.gen.ts` regenerated by the build, not by hand.
2. **Old app keeps working on the new schema.** `main`'s test suite passes against a DB that has
   `0025` + `0026` applied. Reason: production gets the migrations a few minutes **before** the
   new app deploys, so the running old app must survive that window.
3. **Verification docs** exist with real command output:
   `docs/specs/020-session-controls/verification.md`, `docs/specs/021-commissions-builder/verification.md`
   — each maps every acceptance criterion of its spec to the test(s) that prove it.
4. **User journey** `docs/user-journeys/<PR#>-session-controls-and-commissions.md` in simple Gulf
   Arabic, same format as `26-session-recording.md`, plus a row in `docs/user-journeys/README.md`.
5. **One independent `/code-review`** by the coordinator on the whole PR diff; every confirmed
   finding fixed with a failing test first; rejected ones answered with evidence.
6. **CI `verify` green** on the exact head that merges.
7. **Production:** `pg_dump` backup taken, `0025` + `0026` applied with the final reviewed files,
   catalog checks pass, then merge, `lovable` synced, deploy finished, smoke checks pass.
   (Waleed approved the backup and apply for this PR on 2026-11-20.)

Out of scope: payroll/commission payout screens, push notifications, any new feature.

## Part B — Plan

- Create both `verification.md` files. For each acceptance criterion: criterion text → test file and

  counts). No claim without a test reference; mark any criterion without a test as **GAP** instead of
  inventing one.

**Task 4A.2 — User journey draft**
- Write `docs/user-journeys/_draft-020-021.md` (the coordinator renames it once the PR number exists).
- Sections, in Arabic: prerequisites (accounts: owner, branch manager, reception; migrations applied),
  then steps with "المفروض يصير" for: price raise with reason; discount within cap; over-cap with

- End with "اللي ما ينختبر من الواجهة" (e.g. the 5-minute expiry needs waiting).

**Task 4A.3 — Gate run + compatibility check**
1. Full gates from Part A #1 on a fresh container `pospay-020-final` (postgres:16-alpine, trust auth,
   db `pospay_test`, roles `anon`/`authenticated`), then remove the container.
2. Compatibility: in a temporary `git worktree` of `origin/main`, run `bun install` and
   `bun run test` with `POSPAY_TEST_DATABASE_URL` pointing at a DB where the branch's `0001`–`0026`
   are applied. Report failures exactly — do not fix `main`. Remove the temporary worktree after.
3. Skills (docs changed): run `docs-guard` on the three docs and fix what it confirms.
4. Report: files created, gate table with exit codes, compatibility result, docs-guard findings.

### 4B — Coordinator (Claude)

**Task 4B.1 — Review**: run `/code-review` once on `main...HEAD`; reproduce each finding, fix with a
failing test, re-run affected gates. Re-delegate only if a fix is large.

**Task 4B.2 — PR + CI**: open the PR (Heavy, body lists migrations, risks, rollback, production
steps); rename the journey file to `<PR#>-…` and add the README row; link the PR; wait for `verify`.

**Task 4B.3 — Production apply (right before merge)**
1. `pg_dump -Fc` of the production DB inside `supabase-db` to a dated file; record size + sha256.
2. Upload final `0025`, `0026` via sftp; compare sha256 with the PR head files.
3. `docker cp` into the container; `psql -v ON_ERROR_STOP=1 --single-transaction -f` each, in order.
4. Catalog checks: new tables exist with RLS enabled; key functions exist
   (`verify_manager_pin_approval`, `decide_discount_approval`, `editable_session_by_id`,
   `company_member_names`, `salary_date_open`, `discount_within_cap`); `manager_pins` has no grants
   to `pospay_app`; tier backfill row count matches pre-check.
5. If any step fails: stop, do not merge, restore is `pg_restore` from step 1 (Waleed decides).

**Task 4B.4 — Merge + smoke**
1. `gh pr merge <N> --merge --match-head-commit <sha>`; fast-forward `lovable` after the ancestor check.
2. Wait for the Dokploy deploy to finish; check app logs for startup errors.
3. Smoke: app loads; sign-in works; `/pos/sessions` form loads; `/app/services/sessions`,
   `/app/services/approvals`, `/app/commissions/plans` load for an owner; no 500s in logs.
4. Post the 3-part plan summary (done / remaining / recommendation) and the receipt
   (backup file, sha256s, catalog results, deploy id).

**Rollback:** app — redeploy the previous `main` commit in Dokploy; DB — the migrations are additive
for the old app (proved by 4A.3 step 2), so the schema can stay; full restore from the dump only on
Waleed's decision.
